EVARA — Phase 4 Report: Reports, Planner, Dashboard & Progress
==================================================================

IMPLEMENTATION SUMMARY
------------------------
Four new feature areas were added on top of the existing, unmodified
Phase 1-3 conversation/analysis layers:

  - REPORTS: a structured, non-clinical reflection summary generated
    from a conversation's existing Phase 3 analysis (never re-running
    NLP). Persisted per-generation, like Phase 3's analyses.
  - PLANNER: plain CRUD over user-owned action items (pending/
    completed/cancelled), no autonomous recommendation logic.
  - DASHBOARD: a read-only aggregation of a user's conversations,
    plans, reports, and analysis trends, computed live from persisted
    data on every request.
  - PROGRESS: deterministic plan-completion metrics derived from the
    same persisted plan/conversation records.

Every ownership check reuses the existing Phase 2/3 pattern (query
scoped by user_id directly, 404 for both "not found" and "not yours",
400 for malformed ObjectIds) via the existing conversation_service and
analysis_service — no new ownership implementation was written.

API ENDPOINTS ADDED
----------------------
POST   /api/reports/{conversation_id}/generate   (201)
GET    /api/reports/{conversation_id}             (200)
POST   /api/planner                                (201)
GET    /api/planner            (?status=pending|completed|cancelled)
GET    /api/planner/{plan_id}
PATCH  /api/planner/{plan_id}
POST   /api/planner/{plan_id}/complete
DELETE /api/planner/{plan_id}                       (204)
GET    /api/dashboard
GET    /api/progress

All 10 require the existing HTTPBearer JWT authentication.

MONGODB COLLECTIONS / INDEXES
--------------------------------
reports:
  - (conversation_id: 1, user_id: 1, created_at: -1)  — ownership-scoped
    "latest report for this conversation" lookup.
  - (user_id: 1, created_at: -1)  — dashboard's "recent reports across
    all of a user's conversations" query.
plans:
  - (user_id: 1, status: 1, created_at: -1)  — ownership-scoped listing,
    optionally filtered by status, newest first.

Existing users/conversations/analyses indexes are unchanged.

REPORT STRUCTURE
-------------------
{
  id, user_id, conversation_id, analysis_id,
  conversation_title, conversation_stage, conversation_status,
  reflection_summary,      # truncated (400 char) excerpt of the
                            # analysis's own normalized_text — the
                            # user's own words, not a generated summary
  themes, dominant_sentiment, dominant_emotion,
  intent: {label, confidence, is_low_confidence},
  safety_level, safety_note,
  evidence_summary,        # reused directly from the Phase 3 analysis's
                            # evidence.summary — not recomputed
  action_plan,              # EVARA's own stored closure message, only
                            # once the conversation reached "closure";
                            # null otherwise
  created_at
}
No diagnosis, clinical conclusion, or mental-health label anywhere in
this structure — every field is either copied verbatim from stored
Phase 2/3 data or a plain truncation of it.

PLANNER STRUCTURE
--------------------
{
  id, user_id, conversation_id (optional),
  action, date (YYYY-MM-DD, optional), time (HH:MM 24h, optional),
  frequency (free text, optional),
  status: pending | completed | cancelled,
  created_at, updated_at
}
"complete" (POST .../complete) and "cancel" (PATCH status=cancelled)
are distinct: complete marks the item done; cancel marks it abandoned
without deleting it; DELETE removes the record entirely. All three are
explicit, deterministic status/state changes — no inference.

DASHBOARD STRUCTURE
-----------------------
{
  conversation_count, completed_conversation_count, active_conversation_count,
  recent_conversations: [{id, title, stage, status, updated_at}] (up to 5),
  pending_plan_count, completed_plan_count, cancelled_plan_count,
  active_plans: [{id, action, status, date, updated_at}] (up to 5, pending only),
  recent_reports: [{id, conversation_id, dominant_sentiment, dominant_emotion,
                     safety_level, created_at}] (up to 5),
  sentiment_trend: {positive, negative, neutral}  # counts across all of
                    the user's stored analyses
  top_themes: [{theme, count}]  # top 5 by match_count, aggregated
              across all of the user's stored analyses
}
Every number here is a live count/query against persisted documents at
request time — nothing is cached or pre-computed, and nothing is
estimated when there's no data (empty-state test confirms every field
is exactly 0/[]/{positive:0,negative:0,neutral:0} for a brand-new user).

PROGRESS METRICS
-------------------
{
  total_plans, pending_plans, completed_plans, cancelled_plans,
  completion_percentage,   # completed / (completed + pending) * 100,
                            # rounded to 2dp; cancelled plans are
                            # deliberately excluded from the denominator
                            # so a cancelled item doesn't count against
                            # progress; 0.0 when there are no
                            # actionable (pending+completed) plans
  recent_completed_plans: [...] (up to 5, most recently completed first),
  plans_completed_last_7_days,  # simple rolling-window count from
                                  # updated_at timestamps
  total_conversations, completed_conversations
}
No metric here is invented — if a metric couldn't be reliably derived
from existing timestamps/statuses (e.g. a longer historical trend line),
it was left out rather than approximated.

KNOWN LIMITATIONS
---------------------
- "Activity over time" (mentioned as an example Phase 4 progress metric)
  is implemented only as a simple 7-day rolling completed-plan count,
  not a full historical trend series — a genuine multi-week/month trend
  would need either a scheduled aggregation job or a larger reporting
  window design, which felt like scope creep beyond "deterministic
  metrics from existing data" for this phase.
- The dashboard's sentiment/theme trend aggregation iterates a user's
  `analyses` documents in Python rather than using a MongoDB aggregation
  pipeline. This is simple and correct at prototype scale but would
  benefit from a real aggregation pipeline (or pre-computed rollups) if
  a user accumulates a very large number of analyses.
- Reports are generated on-demand (POST .../generate) rather than
  automatically whenever a new analysis is created — this mirrors the
  Phase 3 analysis pattern exactly and was a deliberate choice for
  consistency, not an oversight.
